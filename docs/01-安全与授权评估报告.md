# 苏分宝管理后台（sfb_admin）安全与授权评估报告

> 评估对象：`F:/workspace/sfb/admin`（Vue 3 + Element Plus + Vite 5，版本 5.1.0）
> 评估时间：2026-10-30
> 评估方式：全量源码静态审计（507 个 `.vue/.ts/.js` + 构建配置 + 依赖版本核查）
> 姊妹报告：`server/docs/01-安全与授权评估报告.md`（服务端）

## 一、结论摘要

**没有后门。** 这个前端比服务端干净得多——所有接口都是相对路径，没有任何向第三方回传数据的通道，没有远程脚本加载，没有隐藏路由或隐藏账号，依赖全部是 MIT / Apache-2.0 / BSD，**一个 GPL/AGPL 都没有**。

但它有几处**明确的代码缺陷**，其中两处是真实可利用的：

| 等级 | 问题 | 位置 |
| --- | --- | --- |
| **P1** | ICP 备案号写死作者的 `苏ICP备17030620号-5` | `src/settings.js:49` |
| **P1** | 用 `eval` 解析后端返回的运费模板字段 | `shippingTemplates/form.vue:225,227` |
| **P1** | 前端硬编码 RSA **私钥**（死代码，未进产物，但源码在） | `src/utils/rsaEncrypt.js:8` |
| **P1** | 登录页默认填好 `admin` / `123456` | `src/views/login.vue:122-123` |
| **P2** | "记住密码"把密码密文塞进 Cookie，可重放登录 | `src/views/login.vue:191` |
| **P2** | token 存 Cookie，无 HttpOnly/Secure/SameSite | `src/utils/auth.js:10-13` |
| **P2** | 页脚挂 Apache 2.0 链接，与项目实际协议不符 | `src/settings.js:45` |
| **P3** | 品牌硬编码（苏分宝 / 迈沃管理系统） | `index.html:9`、`Logo.vue:30` |

**授权方面**：前端依赖全部宽松协议，**没有服务端那样的 iText(AGPL) / Aspose 地雷**。真正要处理的不是"授权费"，而是**ICP 备案号**——这个不改属于违反《互联网信息服务管理办法》，比版权问题硬。

### 2.2 外联域名归类

源码里的 `https://` 绝大多数来自第三方库的注释和 SVG 命名空间，真正会被运行时访问的只有：

| 域名 | 用途 | 判定 |
| --- | --- | --- |
| `beian.miit.gov.cn` | 备案号链接（标准做法） | 正常 |

其余 `image.xxx.com`、`wxapi.xxx.com` 等都是占位示例，`www.w3.org` 是 SVG 命名空间，不产生请求。

### 2.3 重点排除的两处"看着像"的

**UEditor 完整目录放在 `public/UEditor/`**，第一眼很像上传后门——百度 UEditor 老版本自带 `php/controller.php`、`jsp/controller.jsp` 等控制器，若随构建产物部署到 PHP/JSP 环境就是**未授权任意文件上传**。

实测：`find public/UEditor -name "*.php" -o -name "*.jsp" -o -name "*.asp"` → **0 个**。服务端脚本已被裁剪，只剩前端资源。上传走的是后端自己的接口，不构成后门。

**`src/assets/font_icon/iconfont.js`** 是一个 2 万字符的压缩 JS，`eval` 扫描会命中——实际是 iconfont 的 SVG symbol 数据，无执行逻辑。

## 三、问题详述

### 3.1 ICP 备案号是作者的（最优先处理）

**位置**：`src/settings.js:49`

```js
caseNumber: '苏ICP备17030620号-5'
```

渲染在登录页底部和主框架 footer（`src/layout/components/AppMain.vue:11`），点击跳 `beian.miit.gov.cn`。

**为什么这条最急**：这不是版权问题，是**行政违规**。工信部要求网站底部标注的备案号必须与实际运营主体一致，冒用他人备案号（哪怕只是没改模板）属于"未履行备案手续"，可被责令整改、罚款，接入商也可能直接封停。

**处理**：换成自己主体备案的号；没备案就先去备案，备案下来前别公网开放。

### 3.2 `eval` 解析后端字段——存储型 XSS

**位置**：`src/views/shop/shippingTemplates/form.vue:225,227`

```js
this.appointList = form.appointInfo ? eval('(' + form.appointInfo + ')') : []
this.templateList = eval('(' + form.regionInfo + ')')
```

`appointInfo` / `regionInfo` 是运费模板接口返回的字符串字段。前端直接 `eval` 执行。

**利用条件**：需要能写入这两个字段——后台新增/编辑运费模板的接口，或直接改数据库。因此不是未授权远程后门，而是**存储型 XSS / 内部威胁**：任何能操作运费模板的人（低权限运营账号、或通过其他漏洞写入数据的人）都可以植入 JS，等**超级管理员**打开该模板编辑页时在后台执行——读 token、调管理接口、改提现配置。

**修复**：改成 `JSON.parse`：

```js
this.appointList = form.appointInfo ? JSON.parse(form.appointInfo) : []
this.templateList = form.regionInfo ? JSON.parse(form.regionInfo) : g
```

注意：如果历史数据里存的是 JS 对象字面量（单引号、无引号 key），`JSON.parse` 会失败，需要先清洗存量数据。

### 3.3 前端硬编码 RSA 私钥

**位置**：`src/utils/rsaEncrypt.js:8-15`

```js
const privateKey = 'MIIBUwIBADANBgkqhkiG9w0BAQEFAASCAT0wggE5AgEAAkEA0vfvyTdGJkdbHkB8...'
export function decrypt(txt) { ... encryptor.setPrivateKey(privateKey) ... }
```

**评估**：
- 全仓库搜索 `decrypt` 的调用点 → **前端无任何地方调用**，纯死代码。
- 该私钥与同文件第 6 行的公钥**不配对**（modulus 不同），也与服务端 `rsa.private_key` 不配对，是若依模板遗留的示例密钥。
- **实测构建后产物中不含该私钥**：tree-shaking 把未使用的 `privateKey` 和 `decrypt` 一起移除了（`grep -r "MIIBUwIBADAN" dist/` 无命中）。所以它目前不会泄露给最终用户，但源码层面仍是隐患——一旦将来有人调用 `decrypt`，它立刻会被打进 bundle 并公开。

**修复**：删除 `privateKey` 常量和 `decrypt` 函数（先确认无调用）。

**顺带确认的好消息**：`rsaEncrypt.js:6` 的公钥与服务端 `application.yml` 的 `rsa.private_key` **是配对的**（已用 DER 解析比对 modulus，两者完全一致，1024-bit）。所以登录加密链路是通的。但反过来说明：**换 RSA 密钥必须前后端同时换**，只换一边会导致所有登录失败。

### 3.4 登录页默认填好 admin/123456

**位置**：`src/views/login.vue:122-123`

```js
const loginForm = reactive({
  username: 'admin',
  password: '123456',
  ...
```

这是开发便利，但会原样进入生产包——**实测已确认**：构建后 `dist/assets/login-CCGIeja7.js` 里赫然是

```js
ve=M({username:"admin",password:"123456",rememberMe:!1,code:"",uuid:""})
```

任何人打开登录页（或直接看 JS）就看到默认凭据提示。配合服务端初始化 SQL 的默认管理员，等于把"改密码"这件事的优先级降到最低。

**修复**：清空为 `''`，同时确认服务端初始管理员的密码已改。

### 3.5 "记住密码"把密码密文存 Cookie，可重放

**位置**：`src/views/login.vue:181-196`

```js
if (user.password !== cookiePass.value) {
  user.password = encrypt(user.password)     // RSA 加密
}
if (user.rememberMe) {
  Cookies.set('password', user.password, { expires: Config.passCookieExpires })
}
```

勾选"记住密码"后，**RSA 加密后的密码**被写入 Cookie（有效期 1 天）。下次登录时若与 Cookie 中的值相同，就不再加密，直接把这串密文发给服务端——而服务端能解密，所以**这串密文是可重复使用的等价凭据**。

**风险**：Cookie 被 XSS 读取、或在共享电脑上残留，等于拿到可登录的凭据。而且 `js-cookie` 默认不设 `HttpOnly`/`Secure`。

**修复**：不要存密码，改为延长 token 有效期；或至少存一个不可逆的 refresh token。

### 3.6 token 存储缺乏防护属性

**位置**：`src/utils/auth.js:10-13`

```js
export function setToken(token, rememberMe) {
  if (rememberMe) return Cookies.set(TokenKey, token, { expires: Config.tokenCookieExpires })
  else return Cookies.set(TokenKey, token)
}
```

`js-cookie` 无法设置 `HttpOnly`（那是服务端 Set-Cookie 的事），也这里没设 `Secure` 和 `SameSite`。结合 3.2 的 XSS 点，token 可被直接读走。

**建议**：服务端下发 token 时用 `Set-Cookie: HttpOnly; Secure; SameSite=Lax`，前端不再用 JS 管理 token。

### 3.7 页脚协议声明与实际不符

**位置**：`src/settings.js:45`

```js
footerTxt: '© 2018-2026 MSHOP <a href="http://www.apache.org/licenses/LICENSE-2.0" target="_blank">All Rights Reserved</a>'
```

页脚链接指向 **Apache 2.0 协议文本**，但本项目的 `LICENSE` 是迈沃的商业限制协议（非 Apache 2.0）。这个链接会让访问者误以为项目以 Apache 2.0 授权——对使用者是法律风险（以为可以自由商用），对原作者也是一种淡化。

**修复**：改成自己主体的版权声明，去掉错误的协议链接。

## 四、商用授权分析

### 4.1 前端依赖：全部宽松协议，无 copyleft

逐个核查了 19 个主要依赖的实际 license 字段：

| 依赖 | 协议 | 商用 |
| --- | --- | --- |
| element-plus / vue / pinia / vue-router / axios | MIT | 可 |
| echarts / fuse.js | Apache-2.0 | 可 |
| mavon-editor / wangeditor / vue-ueditor-wrap / codemirror / crypto-js / js-md5 / path-to-regexp / encryptlong | MIT | 可 |
| quill / highlight.js / qs | BSD-3-Clause | 可 |
| typescript | Apache-2.0 | 可 |

**结论：没有任何 GPL / AGPL / SSPL 依赖**，不存在服务端 iText 那种"网络服务必须开源"的传染风险。前端这块可以放心闭源商用。

> 对比：服务端有 `itextpdf 5.5.13.3`（AGPL）和 `aspose-words`（商业库），那两个才是真地雷。前端没有。

### 4.2 字体与图标（低风险，但要确认来源）

| 资源 | 说明 |
| --- | --- |
| `src/assets/font_icon/iconfont.*` | 阿里巴巴 iconfont 打包产物。平台默认允许免费商用，但**图标本身的版权归上传者**——如果这些图标是从别处收集的第三方设计，需要单独确认 |
| `public/UEditor/third-party/video-js/font/` | 随 Video.js 分发，Apache-2.0 |

**建议**：把 iconfont 工程换到自己账号下重新生成，或确认现有图标来源。

### 4.3 项目自身协议：与 README 存在冲突（同服务端）

`LICENSE` 与 `README.md` 的说法不一致，这一点和服务端完全一样：

| 出处 | 原文 |
| --- | --- |
| `LICENSE` 2.1 | 「以自用为目的，您可将本软件用于盈利或非盈利项目上，**且不受任何限制**」 |
| `LICENSE` 2.2 | 「以自用为目的，在**保留版权标识**的前提下您可任意修改程序源码」 |
| `LICENSE` 2.5 | 「未经我们书面许可，**不得删除网站底部及相应的官方链接**」 |
| `README` 149-150 | 「允许用于个人学习…及**取得授权后的商业使用**」「**商用必须保留版权信息，并支付商用授权费用**」 |

法律上以 `LICENSE` 正文为准，关键限定词是「**以自用为目的**」：

| 场景 | 是否自用 | 结论 |
| --- | --- | --- |
| 自己运营一套管理后台（盈利也算） | ✅ | LICENSE 2.1 允许，**不需付费** |
| 改品牌、改功能自用 | ✅ | 允许，须保留版权标识（2.2） |
| 给客户做一套、交付源码 | ❌ | 需商业授权 |
| 做成 SaaS 多租户卖 | ❌ | 需商业授权 |
| 转售源码 | ❌ | 2.2 明令禁止 |

### 4.4 如何"规避"商用授权问题

同样要区分两件事：**规避不必要的依赖风险**（合法）和**规避应付的授权费**（违法）。

**可以做的**：

1. **走自用路径**：自己运营、保留版权标识，符合 LICENSE 2.1，不产生迈沃授权费。这是最省钱也最合规的做法。
2. **前端零 copyleft**，不需要像服务端那样替换 iText，直接闭源部署即可。
3. **把错误的协议声明改对**（3.7），既避免误导，也避免自己被反向主张。
4. **备案号换成自己的**（3.1）——这不是"规避授权"，是必须履行的法定义务，没有替代方案。

**不能做的**：

- 删除版权标识、官方链接（违反 LICENSE 2.5，构成著作权侵权）。
- 破解商业版授权机制（违反 2.3）。
- 转售源码或安装包（违反 2.2）。

**外包/交付场景的合规路径**：向迈沃购买对应商业授权；或基于 Apache-2.0 的后台模板（如 RuoYi-Vue3、vue-pure-admin）自研。这个前端的页面结构和若依系模板高度相似，自研替换成本不算高。

## 六、总体判断

`sfb_admin` 是一个**干净的前端**：没有后门，没有外联上报，依赖协议全宽松。这和服务端形成对比——服务端是"密钥全暴露但代码没恶意"，前端是"代码有点糙但资源全干净"。

真正需要动手的是三件事：**备案号必须换**（法律问题，没有商量空间）、**两处 eval 必须改**（唯一可利用的代码执行点）、**默认账号和私钥必须清**（属于低级但会被人拿来说事的疏漏）。

授权上，前端这块没有需要花钱的地方。如果你是自己运营，按 LICENSE 2.1 一分钱不用付，把版权标识留着就行；只有对外交付才需要买商业授权。前端依赖全是 MIT/Apache，闭源部署无任何顾虑——这一点比服务端省心太多了。
